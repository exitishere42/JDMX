JDMX – Entwickler-Wiki & Technische Dokumentation

Willkommen im offiziellen technischen Wiki von JDMX (Java DMX Controller). Dieses Wiki dient als zentrales Nachschlagewerk, damit jede Person – auch ohne KI oder externe Werkzeuge – das gesamte System in wenigen Minuten verstehen, warten, Fehler beheben und neue Funktionen einbauen kann.

Autonome Dokumentation Alle Inhalte dieses Wikis liegen lokal auf deiner Festplatte und funktionieren zu 100 % offline. Es gibt keine externen Server-Abhängigkeiten.

Das Gesamtsystem auf einen Blick

JDMX ist ein nativer, plattformübergreifender Desktop-DMX512-Lichtcontroller mit integrierter Show-Timeline (im FL-Studio-Stil), 2D-Bühnen-Visualisierung und hochpräziser Multitrack-Audiowiedergabe.

Schnelleinstieg & Entwickler-Setup

Um JDMX zu kompilieren, auszuführen und weiterzuentwickeln, benötigst du genau zwei installierte Werkzeuge auf deinem Rechner:

1. Voraussetzungen

  • Java Development Kit (JDK) 21 LTS: Empfohlen ist Eclipse Adoptium Temurin 21 oder OpenJDK 21.
  • Apache Maven 3.8+: Das Standard-Build-Werkzeug für das gesamte Projekt.
Versionsprüfung im Terminal: 
java -version
mvn -version
Beide Befehle müssen fehlerfrei antworten und Version 21 bzw. Maven 3.8+ ausweisen.

2. Das Projekt in der IDE öffnen

In IntelliJ IDEA (Empfohlen)

  1. Wähle File → Open...
  2. Navigiere in den Projektordner (wo die pom.xml liegt) und öffne ihn als Projekt.
  3. IntelliJ lädt alle Abhängigkeiten automatisch aus dem lokalen Maven-Cache.
  4. Starte die Anwendung über src/main/java/de/exit/jdmx/JdmxApplication.java.

3. Die wichtigsten Terminal-Befehle

Befehl Auswirkung
mvn test Führt alle 370 Tests aus. Muss vor jedem Commit zu 100 % grün sein!
mvn test -Dtest=TimelineServiceTest Führt nur die Tests einer einzelnen Klasse aus (ideal für schnelles Entwickeln).
mvn package -DskipTests Baut die fertige All-in-One Fat-JAR unter target/jdmx-<version>-all.jar.
mvn javadoc:javadoc Generiert die vollständige HTML-JavaDoc Website unter target/reports/apidocs/index.html.
./build-appimage.sh Baut unter Linux oder WSL das eigenständige jdmx-x86_64.AppImage.

Die 3 goldenen Architektur-Regeln

Diese drei Regeln sind die wichtigste Leitplanke, damit JDMX auch über Jahre hinweg wartbar, fehlerfrei und modular bleibt:

Regel 1: 100 % MVC-Trennung (Keine Logik in JavaFX)

Die Benutzeroberfläche in de.exit.jdmx.ui.* visualisiert ausschließlich Daten und fängt Benutzerklicks ab. Sie führt niemals Berechnungen durch.

  • Verboten in UI-Klassen: DMX-Frame-Berechnungen, HTP/LTP-Mischlogik, direkte Audio-Dekodierung, Schreiben von Socket-Paketen.
  • Pflicht: Klicks oder Slider-Bewegungen rufen sofort eine Methode im entsprechenden Service auf (z. B. dmxService.setChannel(...) oder timelineService.setTrackStartTimeMs(...)).

Regel 2: Thread-Sicherheit & Platform.runLater()

In JDMX laufen mehrere Threads parallel:

  • JavaFX Application Thread: Zeichnet die Fenster und Komponenten (60 FPS).
  • DmxEngine Timer: Sendet stur alle 25 ms DMX-Pakete ins Netzwerk (40 Hz).
  • Audio Playback Threads: Dekodieren MP3/WAV-Streams im Hintergrund.
Kritische Regel: Wenn ein Hintergrund-Thread Daten an die Oberfläche melden möchte, muss dies immer über Platform.runLater(() -> { ... }) synchronisiert werden, da JavaFX sonst eine IllegalStateException wirft!

Regel 3: Test-Driven Development (TDD)

Bevor neuer Produktivcode geschrieben wird, entsteht der Test:

  1. Schreibe den Unit-Test in src/test/java/... (Test schlägt fehl → Rot).
  2. Schreibe den Code im Service/Core, bis der Test durchläuft (→ Grün).
  3. Führe mvn test aus, um sicherzustellen, dass keine bestehende Funktion beschädigt wurde.

DMX-Timing & die 40-Hz-Schleife

DMX512 verlangt eine kontinuierliche, jitterfreie Signalübertragung. Bricht der Datenstrom ab, schalten viele Moving-Heads oder Dimmerpacks in den Notlauf oder gehen aus.

Der 25-Millisekunden-Loop (`DmxEngine.java`)

Die Klasse DmxEngine betreibt einen hochpräzisen Hintergrund-Timer (ScheduledExecutorService):

┌────────────────────────────────────────────────────────┐ │ DMX-ENGINE 40 HZ LOOP │ │ (Läuft alle 25.0 ms ununterbrochen) │ ├────────────────────────────────────────────────────────┤ │ 1. → Lese Snapshot aller 512 Kanäle aus DmxUniverse │ │ 2. → Erzeuge Art-Net UDP-Paket (ArtNetPacketBuilder) │ │ 3. → Sende Frame an Netzwerk-Socket (Port 6454) │ │ 4. → Sende Frame an USB-DMX-Hardware (jusb2dmx FTDI) │ └────────────────────────────────────────────────────────┘
Unabhängigkeit von der Benutzeroberfläche: Selbst wenn die grafische Oberfläche bei aufwendigen Animationen kurzzeitig langsamer rendert, sendet die DmxEngine im Hintergrund mit exakten 40 Bildern pro Sekunde weiter.

DMX-Mischregeln: HTP, LTP & 16-Bit Pan/Tilt

In DmxUniverse.java werden die DMX-Werte aller Kanäle (1–512) nach internationalen Lichtpult-Standards gemischt:

1. HTP (Highest Takes Precedence)

Gilt ausschließlich für Dimmer / Intensität. Wenn mehrere Szenen oder Fader gleichzeitig denselben Scheinwerfer ansteuern, gewinnt der höchste Wert:

int finalValue = Math.max(sceneValue, faderValue);

2. LTP (Latest Takes Precedence)

Gilt für Pan, Tilt, Farbe (RGB/CMY), Gobo und Shutter. Hier gewinnt immer der zuletzt gesendete Steuerbefehl.

Kritischer Schutz vor Wegdrehen: Der Grand Master und die Blackout-Taste dürfen niemals Pan- oder Tilt-Kanäle beeinflussen! Bei Blackout schließt sich nur der Dimmer/Shutter, die Moving-Heads bleiben punktgenau auf ihrer Position stehen.

3. 16-Bit Pan/Tilt Berechnung

Moving-Heads teilen ihre Winkelposition auf zwei DMX-Kanäle auf:

  • Coarse Byte (Grobkanal): Höchstwertiges Byte (MSB).
  • Fine Byte (Feinkanal): Niedrigstwertiges Byte (LSB).
// Normalisierter Wert (0.0 bis 1.0) in 16-Bit DMX umrechnen:
int dmx16 = (int) Math.round(normalizedValue * 65535.0);
int coarse = (dmx16 >> 8) & 0xFF; // Höhere 8 Bit
int fine   = dmx16 & 0xFF;        // Niedrigere 8 Bit

Art-Net UDP Netzwerkprotokoll

Art-Net überträgt DMX-Daten als UDP-Broadcast oder Unicast über Standard-Netzwerkkabel (Ethernet / WLAN):

Spezifikations-Parameter

  • Standard UDP-Port: 6454 (Hexadezimal: 0x1936).
  • OpCode für DMX: 0x5000 (OpOutput / OpDmx).
  • Protokoll-Version: 14 (Hexadezimal: 0x0E).
  • Paketgröße: Exakt 530 Bytes (18 Byte Header + 512 Byte DMX-Nutzdaten).

Paketaufbau (`ArtNetPacketBuilder.java`)

Byte-Bereich Inhalt / Wert Bedeutung
0 – 7 "Art-Net\0" 8 Byte ASCII Identifikation
8 – 9 0x00, 0x50 OpCode OpDmx (Little Endian)
10 – 11 0x00, 0x0E Art-Net Version 14 (Big Endian)
12 sequence Paketzähler (0–255) zur Erkennung verlorener Pakete
13 0x00 Physical Port
14 – 15 universe Universums-Adresse (SubUni & Net)
16 – 17 0x02, 0x00 DMX-Datenlänge: 512 Bytes (Big Endian)
18 – 529 byte[512] Die 512 DMX-Kanalwerte des Universums

Multitrack-Audio-Engine & JLayer

Die Audio-Engine in AudioPlaybackService.java ermöglicht gleichzeitiges, spurunabhängiges Abspielen beliebig vieler paralleler MP3- und WAV-Audiodateien.

MP3-Seeking mit Frame-Genauigkeit

MP3-Dateien besitzen keine feste Millisekunden-Adressierung im Header. Ein MPEG-1 Layer-III Frame bei einer Abtastrate von 44.1 kHz umfasst exakt 1.152 Samples:

// 1152 Samples / 44100 Hz = ca. 26.122 Millisekunden pro Frame
int startFrame = (int) Math.round(offsetMs / 26.122);
mp3Player.play(startFrame, Integer.MAX_VALUE);

Der JLayer AdvancedPlayer überspringt beim Start blitzschnell alle vorherigen Frames und startet die Soundausgabe sofort an der exakten Position.

Live-Resync beim Verschieben von Clips

Wenn du einen Song-Clip während laufender Wiedergabe verschiebst:

  1. Während des Ziehens sorgt ein 80-ms-Debounce-Timer dafür, dass die Audio-Linie nicht bei jedem einzelnen Mauspixel neu geöffnet wird (verhindert Sound-Stottern).
  2. Beim Loslassen der Maus (onMouseReleased) erfolgt ein Sofort-Resync (0 ms Latenz): Liegt die Playhead-Linie im verschobenen Song, springt der Ton sofort an die neue relative Stelle. Liegt der Clip vor oder hinter dem Playhead, stoppt oder startet der Kanal automatisch.

H2-Datenbank & Show-Persistenz

JDMX speichert Show-Dateien und Konfigurationen relational und transaktionssicher:

  • Datenbank-Engine: Eingebettete H2 Database (Version 2.3+).
  • Connection-Pooling: HikariCP für extrem schnelle, thread-sichere Datenbankzugriffe.
  • Modi:
    • jdbc:h2:mem:...: Fluchtige In-Memory-Datenbank für schnelle, isolierte Unit-Tests.
    • jdbc:h2:file:...: Dauerhafte Speicherung auf der Festplatte im Show-Projektordner.

Core-Schicht (`de.exit.jdmx.core.*`)

Die Core-Schicht enthält fundamentale Protokolle, Datenstrukturen und Treiber:

`core.artnet` (Netzwerk-Output)

  • `ArtNetSender`: Öffnet den UDP-Socket auf Port 6454 und versendet DMX-Frames an Unicast- oder Broadcast-Adressen.
  • `ArtNetPacketBuilder`: Serialisiert die 512 Byte DMX-Werte nach Art-Net 4 Spezifikation.

`core.dmx` (DMX-Puffer)

  • `DmxUniverse`: Verwaltet das interne 512-Kanal-Array (Werte 0–255), wendet HTP für Dimmer und LTP für Bewegung/Farbe an und berechnet 16-Bit Pan/Tilt.

`core.model` (Datenmodelle)

  • `TimelineTrack`: Datenklasse für eine Timeline-Spur (Name, zugewiesene Songdatei, Startzeit startTimeMs, Mute-Status).
  • `AudioAnalysisResult`: Speichert Song-Gesamtlaufzeit und normalisierte Hüllkurven-Peaks.
  • `FixtureDefinition` & `FixtureInstance`: Repräsentiert Scheinwerfer-Profile und deren gepatchte Instanzen im Universum.

`core.log` (System-Logger)

  • `AppLogger`: Zentraler Logger mit Dateiausgabe in logs/jdmx.log und Konsole.

Service-Schicht (`de.exit.jdmx.service.*`)

Hier liegt die gesamte Geschäftslogik. Die Services sind Singletons oder thread-sichere Komponenten:

  • `TimelineService`: Taktgeber der Show-Timeline (25ms Intervall), Spuren-Verwaltung, Playback-Status (Play/Pause/Stop), Seeking und Song-Import.
  • `AudioPlaybackService`: Parallele Multitrack-Voice-Engine. Dekodiert MP3s via JLayer und WAV via Java Sound. Verwaltet den verzögerungsfreien Live-Resync beim Verschieben von Clips.
  • `AudioAnalysisService`: Berechnet die Wellenform-Peaks im Hintergrund-Thread (verhindert UI-Lags beim Hereinziehen großer MP3s).
  • `DmxService`: Zentrale Schnittstelle für alle DMX-Kanaländerungen aus der UI zum DmxUniverse.
  • `ProjectStorageService`: Speichert Shows in der eingebetteten H2-Datenbank und lädt sie wieder ein.
  • `UpdateService`: Sucht nach GitHub-Releases und führt In-App-Updates durch.

Show-Timeline UI (`de.exit.jdmx.ui.timeline.*`)

Die Timeline ist im Stil moderner Digital Audio Workstations (FL Studio) aufgebaut:

  • `TimelineMainView`: Obere Transportleiste mit Play-, Pause- und Stopp-Buttons, Zeitanzeige (mm:ss.SSS) und Abfangen der Leertaste.
  • `TimelineGridView`: Das interaktive Canvas-Taktraster:
    • Zeittakt-Lineal oben (Sekunden- und Takt-Markierungen).
    • Playhead-Linie mit orangefarbenem Dreieck (nur am Dreieck verschiebbar).
    • Zeichnen der Song-Clips mit echten Wellenform-Peaks und Startzeit-Offsets.
    • Horizontales Verschieben von Clips per Klick & Drag mit MOVE-Cursor.
  • `TimelineTrackHeaderBox`: Linke Spurenleiste mit runder Mute-LED, Inline-Umbenennung per Doppelklick und [+]-Button für neue Spuren.
  • `ShowTimelineExplorerView`: Rechte Seitenleiste mit Song-Explorer und Drag & Drop-Quelle für das Grid.
  • `TimelineDragHelper`: Erkennt plattformübergreifend externe Audiodateien (Windows Explorer, Linux GNOME Nautilus text/uri-list).

Stage & LightDesk (`ui.stage` & `ui.desk`)

Tab 1: Stage & Fixtures (`ui.stage`)

  • `StageCanvasView`: 2D-Bühne mit U-Traverse, Projektionswand und dynamisch gerenderten Lichtkegeln.
  • `DeviceControlDock`: Unteres 220px Steuerungsdock mit IntensityModuleView (Dimmer), ColorModuleView (Farbrad) und PositionModuleView (2D-XY-Pad für 16-Bit Pan/Tilt).
  • `ProjectExplorerView`: Rechte Seitenleiste für Geräte, Gruppen, Presets und Szenen.

Tab 2: LightDesk (`ui.desk`)

  • `LightDeskWorkspaceView`: Virtuelles 512-Kanal Lichtmischpult.
  • `CanvasDeskView`: Rendert alle 512 Fader auf einem einzigen Canvas-Knoten (Zero-Lag und minimale CPU-Last).
  • `DeskScrollBar`: Eigener taktiler Schieberegler für geschmeidiges horizontales Scrollen.

Rezept: Einen neuen Button in die Benutzeroberfläche einbauen

Schritt-für-Schritt-Anleitung am Beispiel eines neuen Buttons „Alle Spuren stummschalten“:

Schritt 1: Button in der View erstellen

In TimelineMainView.java:

Button btnQuickMute = new Button();
btnQuickMute.getStyleClass().add("timeline-btn");
btnQuickMute.setGraphic(new LucideIcon(LucideIcon.VOLUME_X, 16, Color.web("#EF4444")));
btnQuickMute.setTooltip(new Tooltip("Alle Spuren stummschalten"));

Schritt 2: Event mit dem Service verbinden

btnQuickMute.setOnAction(e -> {
    // Rufe IMMER eine Service-Methode auf, schreibe keine Logik in die View!
    timelineService.muteAllTracks();
});

Schritt 3: Die Methode im Service definieren

In TimelineService.java:

public void muteAllTracks() {
    for (TimelineTrack track : tracks) {
        track.setMuted(true);
    }
    notifyChange(); // Benachrichtigt UI und Audio-Engine über die Änderung
}

Rezept: Ein neues globales Tastaturkürzel registrieren

Angenommen, du möchtest, dass die Taste B jederzeit einen Blackout auslöst:

Schritt 1: Key-Event-Filter in `MainWindow.java`

scene.addEventFilter(KeyEvent.KEY_PRESSED, e -> {
    // 1. Prüfen, ob der Benutzer gerade in einem Eingabefeld tippt:
    Node focusOwner = scene.getFocusOwner();
    if (focusOwner instanceof TextInputControl) {
        return; // Normal weitertippen lassen!
    }

    // 2. Taste abfragen:
    if (e.getCode() == KeyCode.B) {
        dmxService.toggleBlackout();
        e.consume(); // Verhindert weitere Weiterleitung des Events
    }
});

Rezept: Einen Unit-Test schreiben (TDD-Workflow)

So sicherst du eine neue Funktion mit JUnit 5 und AssertJ sauber ab:

  1. Öffne src/test/java/de/exit/jdmx/service/TimelineServiceTest.java.
  2. Füge die Testmethode ein: 
    @Test
@DisplayName("Sollte alle Spuren auf einmal stummschalten")
void shouldMuteAllTracks() {
    TimelineService service = new TimelineService();
    service.addTrack("Track 2");

    // Ausführung
    service.muteAllTracks();

    // Überprüfung mit AssertJ
    assertThat(service.getTracks())
        .allMatch(TimelineTrack::isMuted);
}
  3. Führe den Test im Terminal aus: 
    mvn test -Dtest=TimelineServiceTest
  4. Wenn der Test rot ist: Implementiere die Funktion im Service, bis der Test grün wird!

Fehlerdiagnose: „Kein DMX-Signal am Scheinwerfer“

Wenn Scheinwerfer nicht reagieren, gehe diese 4 Schritte der Reihe nach durch:

1. Log-Datei prüfen (`logs/jdmx.log`)

Siehst du dort Einträge wie [DMX-CHANGE] Uni=1 Ch=1 Val: 0 -> 255? Wenn ja, verarbeitet JDMX deine Fader-Eingaben intern einwandfrei.

2. Art-Net Netzwerkeinstellungen (Tab 5: I/O Patch)

  • Steht Art-Net auf der richtigen Netzwerkkarte (IP-Bereich z. B. 192.168.x.x oder 2.x.x.x)?
  • Ist das Universum richtig zugewiesen? Achtung: Viele Art-Net-Nodes beginnen bei 0 zu zählen (Universum 1 in JDMX = Universum 0 auf der Node).

3. Firewall (UDP-Port 6454)

Art-Net benötigt freigegebenen UDP-Port 6454. Unter Linux prüfen:

sudo ufw allow 6454/udp

4. Gegenprüfung mit `artnet2view`

Starte das Schwestertool artnet2view im selben Netzwerk. Wenn dort Pakete ankommen, sendet JDMX fehlerfrei und das Problem liegt am DMX-Kabel oder Empfänger-Gerät.

Fehlerdiagnose: „Audiodatei spielt nicht ab“

Wenn eine MP3/WAV keinen Ton ausgibt:

1. Fehlermeldung im Log prüfen

Suche in logs/jdmx.log nach Einträgen mit [AUDIO-PLAYBACK]. Bei defekten oder exotischen MP3-Dateien meldet JLayer den genauen Frame-Fehler.

2. Audio-Mixer unter Linux prüfen

Java Sound benötigt ein funktionierendes Standard-Ausgabegerät über ALSA, PulseAudio oder PipeWire. Prüfe im Terminal:

pactl info

3. Mute-Status & Startzeit

Prüfe in der Timeline, ob die Spur versehentlich stummgeschaltet ist (runde Mute-LED) oder ob der Song-Clip weit rechts liegt und der Playhead ihn noch gar nicht erreicht hat.
